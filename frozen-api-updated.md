# Frozen API — Mythras Imperative

**Frozen as of v1.4.278 (roadmap Phase 2f), 4 members added v1.4.296.** Every signature on this page —
all 16 `game.system.api` members plus `SE_RESOLVERS` — is a stability
commitment: **do not change a frozen signature's shape (parameters, return
type, or observable behavior) without a major version bump, and update this
doc in the same change as the runtime.** A signature change here is a
breaking change for every listed caller (the Destined module today; the
planned node editor and third-party modules in the future).

**Membership is CI-enforced as of the repo hygiene sweep (H7): `frozen-api.json`
is a flat manifest of the current `game.system.api` member names, and
`tests/frozen-api.test.js` (pure text-level, no Foundry globals) asserts
set-equality between that manifest and the real `Object.freeze({...})` block
in `mythras.mjs` on every `npm test` run — a member added or removed without
updating `frozen-api.json` in the same commit now fails the suite, which
already runs in CI.** This is deliberately a membership check only — it
cannot validate a signature's shape, so **signature drift on an existing
member is still a documentation-only commitment**, not CI-enforced; no
automated check currently fails a build that silently changes a frozen
signature's parameters or return type. The discipline for THAT half still
lives in this header and in the "update the doc in the same change" rule
below, which this doc's own change log shows has already been missed twice
historically and caught in later doc-sync passes, not by tooling. Signature
validation is left for the node editor's own conformance tests (see the
design brief) — the membership check above is the cheap 80%, not the whole
100%.

Signatures on this page are called directly by external consumers (the
planned node editor, modules, macros). **Do not change a frozen signature
without updating this doc and the runtime in the same change.** A signature
change here is a breaking change for every caller listed.

This file did not exist before v1.4.250 — it is being initialized with the
entries verified as part of the HP-max lock work. It is not yet a complete
audit of every frozen surface in the codebase; expand it as other
already-frozen entry points are confirmed.

**`game.system.api` currently has 16 members** (`mythras.mjs`'s
`Object.freeze({...})` assembly block as of v1.4.296; the exact line range
drifts as the file changes — the count itself is now the CI-enforced part,
via `frozen-api.json` above, so treat any cited line numbers as approximate)
— count this table's `game.system.api.*` rows against that number whenever
either changes; a mismatch means this doc has drifted. This header's own
rule (update the doc in the same change as a frozen signature) was missed
for two consecutive additions — `getArmourAt`
(v1.4.267) and `triggerOpposedSE`
(v1.4.271) both shipped without a row here until this doc-sync pass added
them — worth stating plainly rather than letting a third miss go unremarked.
`triggerFollowUpAttack` (v1.4.272), `applyMythrasTheme` (v1.4.275),
`explainHookSum` (v1.4.277), and `resolveOpposedRoll`/`resolveDifferential`/
`woundLevel`/`woundState` (v1.4.296) all got their row in the same change
they shipped.

| Symbol | Signature | Caller(s) | Notes |
|---|---|---|---|
| `SE_RESOLVERS` | `{ [seId: string]: (ctx) => Promise }` | Node editor (planned), `CombatEngine._resolveOpposedSEs`, `_afterDefenceResolved` | Exported from `module/combat/effects/index.js`. Keys match `id` in `CONFIG.MYTHRAS.specialEffects`. |
| `game.system.api.syncHitLocationHP` | `(actor: Actor) => Promise<void>` | Destined module, macros, GM console | Sole writer of hit-location item `system.hp` (max). Attached in the `ready` hook via `Object.freeze({ syncHitLocationHP })`. Also exported from `mythras.mjs` for internal use by the `updateActor` hook. See `extension-point-api-updated.md` for the `hitPointBonusHooks` contract it consumes. Idempotent — safe to call repeatedly; only writes locations whose computed max differs from the stored value. |
| `game.system.api.determineOutcome` | `(result: number, target: number, rawSkill?: number) => 'critical'\|'success'\|'failure'\|'fumble'` | Destined module (`module/utils/roll-gating.js`), planned node editor | **The canonical unopposed skill grader.** Exported from `module/utils/roll-math.js`; also the function `CombatEngine`/`CharacterSheet` itself uses internally for every skill and combat roll, so a module calling this is guaranteed to match engine grading exactly, not a lookalike. `result` is the rolled d100; `target` is the effective skill after difficulty; `rawSkill` (defaults to `target`) is the pre-difficulty skill, consulted only for the fumble threshold (99 fumbles when `rawSkill < 100`; 100 always fumbles regardless). **This is the intended path for modules building roll-gated mechanics — call this rather than reimplementing crit/fumble bands independently.** Pure, no side effects, safe to call from anywhere once `ready` has fired. `module/utils/combat-math.js` has a second, functionally-identical copy of this function used internally by opposed resolution — that copy is **not** exposed here; `roll-math.js` is the canonical, documented home. **Not yet deduplicated system-side** — no dedicated known-issues tracking doc exists in this repo to log that against (the module repo has `PHASE4-STATE.md`'s "On the Horizon" for this purpose; this repo has no equivalent), so it's recorded here instead until one exists. |
| `game.system.api.shiftGrade` | `(gradeId: string, steps: number) => string` | Destined module (boosts whose effect scales with success grade) | Shifts a difficulty-grade id along `GRADE_ORDER` by `steps` (negative = easier, positive = harder), clamped to the ends of the list. Grade-scaling primitive, not an outcome grader — pairs with `determineOutcome`/`GRADE_ORDER`/`applyDifficulty` as one toolkit, all from `roll-math.js`. |
| `game.system.api.GRADE_ORDER` | `string[]` (7 entries: `veryEasy`…`hopeless`) | Destined module, `shiftGrade`'s own consumers | The canonical ordered list of difficulty-grade ids `shiftGrade` walks along. Frozen array reference (the object itself is not deep-frozen, but nothing in the system mutates it and callers must not either). |
| `game.system.api.applyDifficulty` | `(skill: number, difficulty: string) => number` | Destined module (boosts that roll at a stated difficulty grade) | Applies a difficulty-grade multiplier to a raw skill value, per `DIFFICULTY_GRADES`. Returns the skill unchanged if `difficulty` doesn't match a known grade or is `'hopeless'` (multiplier `null`, meaning "cannot be attempted," not "multiply by null"). |
| `game.system.api.DIFFICULTY_GRADES` | `{ [gradeId: string]: { multiplier: number\|null } }` | Destined module (callers of `applyDifficulty` wanting the raw table) | The multiplier table `applyDifficulty` reads. Exposed alongside `applyDifficulty` specifically so a caller doesn't have to guess the multiplier for a grade it wants to display or validate against. |
| `game.system.api.requestSkillCheck` | `async (actor: Actor, { skillNames?: string[], difficulty?: string\|null, title?: string, prompt?: string, lastCardId?: string\|null, allowGMOverride?: boolean }) => { chosenSkillName: string\|null, chosenSkillTotal: number\|null, chosenSkillRaw: number\|null, roll: number\|null, grade: string\|null, succeeds: boolean, cancelled: boolean, gmOverride: boolean, reason?: string }` | Destined module (Blast Ongoing Damage and future `needsRoll` boosts) | General-purpose "target rolls a skill, tell me the grade" capability — the dialog appears on the owning player's client for a PC and the GM's client for an NPC (routes through the existing `_findDefenderUserId` rule), or is fully automated with no dialog under manual/full automation levels (matches `resolveGripBreakFree`'s own undifferentiated branch). `skillNames` defaults to `['Endurance']`; names the actor doesn't have are silently skipped, order preserved. `difficulty` (a `DIFFICULTY_GRADES` key) is applied via `applyDifficulty` before grading with `determineOutcome`; `succeeds` is a plain boolean derived from `grade` so simple callers can ignore grades entirely. `allowGMOverride: true` adds a "No Check Needed" button, visible only when `game.user.isGM` is true on the client the dialog actually renders on — resolves `{ gmOverride: true, succeeds: true }`. Two failure/decline paths are distinguished by a `reason` field: `reason: 'no-skill'` (none of `skillNames` exist on the actor — checked before any dialog/socket call) and `reason: 'timeout'` (the `CombatSocket.seChallenge` 5-minute timeout elapsed) — both set `cancelled: true` rather than throwing or silently treating a decline as a pass. Dismissing the dialog also resolves `cancelled: true`, never leaves a caller hanging. Safe to call with no active combat. Drives the new generic `seType: 'skillCheck'` case in `runSEDialog` (`module/combat/effects/helpers.js`) — see `extension-point-api-updated.md` for that dialog's own payload contract. |
| `game.system.api.getArmourAt` | `(defender: Actor, locationId: string) => number` | Destined module (`damageHooks` consumers needing to read armour without reaching into `CombatEngine` internals) | Eighth entry on the frozen surface when added (v1.4.267) — thin wrapper over `CombatEngine._getArmourAt`. Returns **base** armour (natural + worn + `armourBonusHooks`, minus sunder) — **not** effective armour: no ammo-piercing reduction, no `apReductionHooks`, no Bypass Armour. Wrapped in try/catch and clamped non-negative, so a missing actor, missing location, or unknown id returns `0` and the call never throws. Deliberately does **not** expose `_getEffectiveArmourAt` — handing back a chokepoint that already consults `apReductionHooks` would invite a hook-reads-its-own-output feedback loop. See `extension-point-api-updated.md`'s `apReductionHooks` section for the related, later read-time hook this complements. |
| `game.system.api.triggerOpposedSE` | `(seId: string, ctx: object) => Promise` | Destined module (Combat Expert Grappling Expertise's Trip/Disarm buttons) | Added v1.4.271. Invokes an `'opposed'`-phase Special Effect resolver directly from `SE_RESOLVERS`, entirely outside the normal attack-roll pipeline — no attack roll, no differential, no SE-count gate. **Not a blanket guarantee for every SE in the catalog** — confirmed safe only for `tripOpponent`/`disarmOpponent`, both of which run their own self-contained resistance roll from `ctx.attacker`/`ctx.defender`/`ctx.seWinner` alone with no dependency on fields only a genuine attack context populates. Other catalog entries (`bleed`/`impale`/`grip`, etc.) assume things like `ctx.chatMessageId` for card-sequencing or upstream trait-restriction checks that only hold inside the real attack flow — calling this for one of those without first confirming its resolver's actual field dependencies is not covered by this entry's "confirmed safe" claim. An unregistered `seId` warns and no-ops rather than throwing; a resolver's own throw propagates uncaught. |
| `game.system.api.triggerFollowUpAttack` | `(attacker: Actor, weapon: Item) => Promise` | Destined module (Close Combat Attack Mega Boost "Berserk Barrage") | Added v1.4.272. Thin wrapper over `CombatEngine._resolveDefender` + `_buildContext` + `_runDialog` — fires a genuine second attack through the exact same pipeline any normal attack uses (real Attacker Dialog, AP spend, roll, defence, damage, further SEs), against whichever token the current user has targeted on the canvas. Not a simulation and not scoped to any one weapon type — any real weapon item owned by `attacker` works, including the module's own bare `type:'weapon'` power-created items. Missing `attacker`/`weapon` warns and no-ops; no resolvable single target (`_resolveDefender` returns `null`) stops silently — `_resolveDefender` has already posted its own "target a token"/"target exactly one token" warning, so this wrapper doesn't duplicate it. A downstream throw (inside `_runDialog`) propagates uncaught, same as `triggerOpposedSE`. `module/combat/effects/flurry.js` (the system's own first consumer of the underlying `_buildContext`+`_runDialog` pair) does NOT go through this wrapper — same-repo code with its own ctx already has a defender (the triggering attack's own target), so it calls `CombatEngine` directly rather than re-resolving canvas targeting it doesn't need. |
| `game.system.api.applyMythrasTheme` | `() => void` | Destined module, any code holding a popped-out window's own `document` | Added v1.4.275. Reads the client-scoped `mythras-imperative.theme` setting (`auto`/`light`/`dark`), resolves `auto` against Foundry core's own `uiConfig.colorScheme.interface`, and stamps `data-mi-theme` on `document.documentElement` — in dark mode also writing every `--mi-*` dark-palette override as an **inline style** on the root element (not a CSS rule; a `:root[data-mi-theme="dark"]` override rule was tried first and silently lost to Foundry v14's `@import layer(system)` CSS layering, where an unlayered rule always beats a layered one regardless of specificity). Runs automatically on `setup` and on the setting's own `onChange`. Exposed here specifically for a popped-out window (Foundry's "Pop Out" on a chat card/app opens a **separate** browser window with its own `<html>` document, which never receives the setup-time stamp or any later `onChange` re-run against the main window) — a caller holding a reference to that window's `document` should call this again with the window focused, or more simply re-run it after swapping `document.documentElement` for the popped-out one. Idempotent, safe to call repeatedly; no return value, no arguments. |
| `game.system.api.explainHookSum` | `(hookFamilyName: string, args?: any[], options?: { errorLabel?: string, clampNonNegative?: boolean }) => { total: number, breakdown: { name: string, value: number }[] }` | Console/macro use, a planned debug UI | Added v1.4.277 (`module/utils/modifier-bus.js`'s `sumHookContributions`, the shared implementation now backing all ten read-time additive numeric hook families — see `extension-point-api-updated.md`'s new "Modifier bus" section). Looks up `CONFIG.MYTHRAS[hookFamilyName]` (an unknown/missing name degrades to `[]`, not a throw) and sums it against `args` exactly as that family's real call site would, returning the total plus a per-hook breakdown — the "why is this number 14?" provenance win. **Diagnostic only**: does not replicate a family's own surrounding math (the AP/movement floor, the healing-rate ×2 hero-advantage doubling, powerPointsHooks having no system base, etc.) — only the raw hook sum. For `apReductionHooks` specifically, pass `{ clampNonNegative: true }` to match its real per-hook floor-at-0 contract. A hook's breakdown entry is named `fn.destinedHookName` (stamped by the Destined module's `registerHook` as of module v1.9.96, from that call's own `feature` string) falling back to `fn.name`, falling back to `'anonymous'` for a hand-rolled registration that bypasses `registerHook` entirely. A throwing hook is caught and logged (`errorLabel` defaults to `hookFamilyName`) and contributes `0`, same isolation as every hook family already had — this wrapper adds no new failure mode. |
| `game.system.api.resolveOpposedRoll` | `(attackerRoll: number, attackerTotal: number, defenderRoll: number, defenderTotal: number) => boolean` | Destined module (Telepathy's opposed-Willpower boosts, CFI-shaped Resist mechanics), planned node editor | Added v1.4.296 (`module/utils/combat-math.js`). Pure — four numbers in, `true` if the defender wins (resists). Same rules-p.24 adjudication `CombatEngine`'s own opposed-SE system (Bleed, Trip, Entangle, Grip, Impale) already uses internally; a caller composes it from two independent `requestSkillCheck` results rather than needing a dedicated "opposed check" flow — `requestSkillCheck`'s own return shape already carries the two numbers this function consumes. Withheld from `game.system.api` since v1.4.244 pending "the first opposed-boost family" needing it; exposed now that one exists (see `CHANGELOG.md`'s v1.4.296 entry). |
| `game.system.api.resolveDifferential` | `(attackOutcome: 'critical'\|'success'\|'failure'\|'fumble', defenceOutcome: 'critical'\|'success'\|'failure'\|'fumble'\|'none') => { seWinner: 'attacker'\|'defender'\|'none', seCount: number }` | Destined module, planned node editor | Added v1.4.296 (`module/utils/combat-math.js`). Pure — implements the rules-p.25 differential table exactly, turning an opposed win into a Special Effect count. Exposed alongside `resolveOpposedRoll` rather than held back further: withholding it would only invite a module to hand-roll the same table by hand, the identical reimplementation-drift risk `determineOutcome`'s own table row above warns about — Destined's own `PERIL_OUTCOME_RANK` is already exactly that drift once, for the opposed-roll adjudication half. |
| `game.system.api.woundLevel` | `(damage: number, maxHp: number, newCurrent: number) => 'none'\|'minor'\|'serious'\|'major'` | Destined module (two independent inline reimplementations of this exact threshold logic, confirmed via its own demand inventory) | Added v1.4.296 (`module/utils/combat-math.js`). Pure — classifies a damage **event**: "what wound did this hit cause." Returns `'none'` whenever `damage <= 0`, regardless of `newCurrent` — this is the function `CombatEngine._applyDamage` and its siblings already call internally at every damage-time write of `system.wound`. See `woundState` below for the companion **state** classifier (a different question, not a duplicate) added the same version. |
| `game.system.api.woundState` | `(current: number, maxHp: number) => 'none'\|'minor'\|'serious'\|'major'` | Destined module (Second Wind and any future power reading/writing HP outside the damage path) | Added v1.4.296 (`module/utils/combat-math.js`). Pure — classifies a hit location's **current state** from its HP alone: "what wound is this location at right now," independent of how it got there. Same `-maxHp`/`0` thresholds as `woundLevel`, just gated on `current` directly rather than a damage delta (`current >= maxHp` → `'none'`). Added because `system.wound` was, until the same-version `preUpdateItem` hook on hit-location items (`mythras.mjs`, not part of the frozen API itself — an internal chokepoint, not a caller-facing member), only ever written at damage time; healing, natural Regeneration, and direct GM edits to Current HP left a location's wound flag stale indefinitely. That hook now calls this function automatically for every hit-location update where `system.current` changes and the caller hasn't already set `system.wound` itself — most callers, including Destined's Second Wind, will never need to call `woundState` directly, but it's exposed for any caller computing a wound category for display or validation without writing through the item. |
