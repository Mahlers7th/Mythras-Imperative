# Frozen API — Mythras Imperative

**Frozen as of v1.4.278 (roadmap Phase 2f), 4 members added v1.4.296, 1 more v1.4.298.** Every signature on this page —
all 17 `game.system.api` members plus `SE_RESOLVERS` — is a stability
commitment: **do not change a frozen signature's shape (parameters, return
type, or observable behavior) without a major version bump, and update this
doc in the same change as the runtime.** A signature change here is a
breaking change for every listed caller (the Destined module today; the
third-party modules).

**Membership is CI-enforced as of the repo hygiene sweep (H7): `frozen-api.json`
is a flat manifest of the current `game.system.api` member names, and
`tests/frozen-api.test.js` (pure text-level, no Foundry globals) asserts
set-equality between that manifest and the real `Object.freeze({...})` block
in `mythras.mjs` on every `npm test` run — a member added or removed without
updating `frozen-api.json` in the same commit now fails the suite, which
already runs in CI.** This is deliberately a membership check only — it
cannot validate a signature's shape, so **signature drift on an existing
member is still a documentation-only commitment**, not CI-enforced; no
automated check currently fails a build that silently changes a frozen
signature's parameters or return type. The discipline for THAT half still
lives in this header and in the "update the doc in the same change" rule
below, which this doc's own change log shows has already been missed twice
historically and caught in later doc-sync passes, not by tooling. Signature
validation remains unsolved and is now unowned — the node editor that was
to have brought its own conformance tests is cut from the project
(2026-09-12). The membership check above is the cheap 80%, not the whole
100%.

Signatures on this page are called directly by external consumers (the
modules, macros. **Do not change a frozen signature
without updating this doc and the runtime in the same change.** A signature
change here is a breaking change for every caller listed.

This file did not exist before v1.4.250 — it is being initialized with the
entries verified as part of the HP-max lock work. It is not yet a complete
audit of every frozen surface in the codebase; expand it as other
already-frozen entry points are confirmed.

The four: the grade table defines grades as operations on *"the skill value"*; the critical bullet glosses that identical phrase as including modifiers; p51 says the over-100% test is *"calculated after any other modifiers for circumstances have been applied"*; and Mju's Saga (p160) computes an over-100 penalty from a base 80% doubled to 160%, which a base-value reading makes impossible. | `game.system.api.replenishLuckPoints` | `async ({ includeAll?: boolean, actors?: Actor[] } = {}) => { updated: number, failed: {name, error}[] } \| null` | GM hotbar macro, the system's own settings-menu button, a module owning its own session lifecycle | Added v1.4.325 (`module/rolls/luck-replenish.js`). The start-of-session refill: *"until the next game session when they replenish to their normal value"* (Imperative p.7, restated p.33). **GM-gated and always confirmed** — it shows the GM a per-actor `current → max` table and returns `null` if cancelled, so it is never a silent mass write. Returns `null` for a non-GM caller too, after a warning notification; it does **not** throw, and it does **not** route through a socket, so calling it on a player client accomplishes nothing rather than half a thing. "Normal value" reads the **derived** `attributes.luckPoints.max`, recomputed each prepare pass from POW, Hero Level advantages and `luckPointsHooks` — so a module's grant (Destined's Lucky ×2 / Mega Lucky ×4) is honoured automatically with no coordination. Writes exactly `max`, never above: `CharacterData#prepareDerivedData` clamps `value > max` back down, so an over-write would silently revert. Defaults to **actors of type `character`** (*"Luck Points help differentiate heroes from the rank and file"* — in this system that line is the actor type, with `npc`/`creature`/`merchant`/`vehicle` as the rank and file); `includeAll: true` takes in every actor with a pool, and `actors` overrides the candidate list entirely for a caller that tracks its own roster. **Note for module authors: the axis is type, NOT `hasPlayerOwner`.** That was the first rule implemented and live testing killed it — every PC in the Destined campaign world is GM-owned, so an ownership rule selected nobody at all. Ownership says who may open a sheet; it is not a claim about who is a hero. Actors already at max are listed in the dialog but not written, so a second run in the same session is a no-op rather than a pile of empty updates. One actor's failed update is caught, logged and reported in `failed` rather than aborting the rest of the party. **Deliberately not hooked to any automatic signal** — Foundry has no "session" concept, and every proxy for one (world startup, a user connecting, a new combat) refills wrongly on a mid-evening restart or a prep session, silently and generously; a refill that is too generous is the bug class nobody reports. The GM says when a session begins. Pure planning half (`luckReplenishPlan`, `applyLuckReplenish`) is exported from the same module and unit-tested, but is **not** part of the frozen surface. |

## Change log

- **v1.4.325** — `game.system.api.replenishLuckPoints` added — eighteenth entry, see the table row above and `CHANGELOG.md`'s own v1.4.325 entry. Closes the last non-Cheat-Fate gap in the Luck Point audit: all three book uses (Cheat Fate, Desperate Effort, Mitigate Damage) plus session replenishment now exist. See the table row and `CHANGELOG.md`'s v1.4.318 entry.
