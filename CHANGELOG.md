## v1.4.287 — August 2026
- **Initiative tie-break (rules p.35, the last open finding from the 2026-08-01 rulebook audit)**: "When two or more participants tie scores, the one with the higher DEX will act first. If this still results in a tie, have each roll a die with high roll going before the other." Foundry core's default Combat Tracker sort only compares the rolled initiative value, falling back to document id — DEX was never consulted, and a tie always resolved arbitrarily.
- New `MythrasCombat` class (`mythras.mjs`, registered as `CONFIG.Combat.documentClass`, same pattern as the existing `MythrasCombatant` extension below it) overrides `_sortCombatants` to compare initiative, then DEX, then a final tie-break.
- The "roll a die" step is a deterministic per-combatant/per-combat hash (`initiativeTieBreakSeed`, FNV-1a-style) rather than live `Math.random()` — this keeps turn order stable across tracker re-renders instead of reshuffling every repaint; it only produces a new outcome when a genuine initiative reroll changes the tied values themselves.
- Comparator logic (`compareInitiative`, `initiativeTieBreakSeed`) lives in `module/utils/combat-math.js`, not inline in `mythras.mjs` — zero-Foundry-dependency, directly unit-testable, matching this file's established "pure math extracted for testability" convention.
- 12 new tests in `tests/combat-math.test.js`, 515/515 pass. Live-verified via Playwright against a real Combat/Combatant pair: tied initiative with differing DEX sorts the higher-DEX combatant first, order is stable across repeated reads, and a full tie (same initiative and DEX) falls back to a stable (non-flickering) hash-based order.
- Closes the last open item from the 2026-08-01 rulebook audit — see `project_rulebook-audit-2026-08-01` memory; that pass's other findings were resolved in v1.4.280-283, and 3 items were deliberately left narrative per Chris's call.

## v1.4.285 — August 2026
- **Diving Strike creature trait automated** (rules p.77) — "This is effectively charging for creatures which are not land based. Diving Strike increases both the Size of the attack, and the creature's Damage Modifier by one step, for this attack only." A new melee-only toggle in `AttackerDialog`, shown only for attackers with the trait, sets `ctx.isCharge = true` (so every existing Charge-gated consumer — damage step-up, and now weapon size, see below — applies for free) plus a separate `ctx.isDivingStrike` flag so the chat card correctly shows a "Diving Strike" pill instead of "Charge". Deliberately does **not** impose Charge's Hard-difficulty penalty, which the rulebook never mentions for this trait. The once-per-round and altitude/depth prerequisites are GM-adjudicated, same as Charge's own preconditions already are.
- **Found and fixed a real, separate, pre-existing bug while building this: Charge's own "Weapon size +1" was never implemented.** The dialog's own hint text has always promised "Weapon size +1, Damage Modifier +1, Hard difficulty" — Damage Modifier and Hard difficulty both worked correctly, but weapon size was never actually applied anywhere. Traced every real consumer of attack-weapon size (`resolveParryReduction` and `resolveWardReduction`, the only two call sites of `_getWeaponForce(..., 'attack')` in the engine) and confirmed neither ever read `ctx.isCharge`. This has silently affected every Charge attack in the game since Charge shipped, not just this new trait. Fixed in both functions — a Charging (or now Diving-Striking) attacker's effective weapon Size now correctly steps up by one for parry/ward reduction purposes.
- **Also found, not fixed**: `combat-math.js` has its own independent `resolveParryReduction(atkSize, defSize, opts)` — a lower-level pure function with its own `combat-math.test.js` coverage — that `CombatEngine.resolveParryReduction` (the one just fixed, and the only one any real gameplay code calls) never delegates to. The dedicated unit tests for "parry reduction" in this codebase have therefore never covered the code path players actually hit. Flagged for a future consolidation pass, not fixed here — same shape as the `determineOutcome`/`DIFFICULTY_GRADES` duplication found and fixed in v1.4.282/283, but this one wasn't touched this round to keep Diving Strike's own diff bounded.

Diving Strike's dialog row appears only for a trait-holding attacker, is melee-only (hidden for ranged weapons, matching Charge), and the resulting context correctly carries `isCharge: true, isDivingStrike: true, difficulty: 'standard'` (no Hard-difficulty leak) after toggling it and confirming.

## v1.4.284 — August 2026
- **Creature trait automation — 3 more of the 38 canonical traits wired**, per [[project_rulebook-audit-2026-08-01]]'s named candidates. 9 of 38 now automated.
- **Multi-Headed / Multi-Limbed** (rules p.77). "One extra Combat Action per extra head/limb-pair beyond the first" — confirmed against rules p.19 that a Combat Action costs one Action Point in this engine, so this is a flat AP-max bonus. `CreatureData.prepareDerivedData` now reads the trait's `system.value` (the extra count, GM-set) and adds it to `attributes.actionPoints.max`, live re-derived on every prepare cycle — no push/stored copy. Dynamic loss as heads/limbs are incapacitated is GM-adjudicated; there's no per-head/per-limb health model in this system to hook automatic loss into.

Auto-applies the existing Grip Special Effect on any successful damage-dealing hit, no SE slot spent, no differential win required. Placed inside `CombatEngine._applyDamage` — the single damage-write chokepoint both Full Auto and Semi-Auto already funnel through (confirmed by reading both call sites) — rather than the two-separate-automation-level treatment an earlier draft of this change used; that draft was reverted once `_applyDamage`'s existing Vampiric-trait block made the simpler single site obvious. The rulebook's separate parry-interaction clause (Grip-vs-limb or Pin-Weapon-vs-weapon instead, depending which side parried) is left to the GM, documented in the trait's description rather than guessed at in code.

No automatic resistance roll — the rulebook's own "varies per creature" framing means there's no single mechanic to automate; left to the GM.

## v1.4.283 — August 2026
- **Rulebook-audit finding #4 fixed: missing 01-05 auto-success / 96-00 auto-failure floor-ceiling.** Rulebook p.18, verified against the primary source: "Any roll of 01-05 is always a Success" and "Any roll of 96-00 is always a Failure, irrespective of how high the skill's value" (unless it's already a Fumble). `determineOutcome` never implemented either rule — a roll of 96-99 against a skill ≥96 auto-succeeded, and a roll of 01-05 against a skill under ~5 (a heavily-penalized or very low starting skill) auto-failed, both backwards from the rulebook.
- **The audit called this "a narrow edge case" — it wasn't.** `determineOutcome` turned out to have **four independent copies**: the frozen, `game.system.api`-exposed one in `roll-math.js`; a byte-identical duplicate in `combat-math.js`, which is the function `resolveOpposedRoll` calls internally — and `resolveOpposedRoll` is the core mechanic behind essentially every opposed Special Effect roll in the game (Bleed, Trip, Entangle, Grip, Impale, and more, across dozens of call sites in `opposed.js`/`helpers.js`/`entangle.js`/`grip.js`/`impale.js`); `MythrasRoll.determineOutcome` (plus a dead, unreachable line with a stale comment claiming a "skill < 50" threshold that doesn't match the rule anywhere — removed); and `CombatEngine._determineOutcome`, a 2-arg variant with no separate raw-skill parameter.
- **Fixed once, consolidated everywhere**: the floor/ceiling logic now lives only in `roll-math.js`'s `determineOutcome`. `combat-math.js` re-exports it directly (no second implementation). `MythrasRoll.determineOutcome` and `CombatEngine._determineOutcome` are now thin delegating wrappers, keeping their existing call-site signatures (3-arg and 2-arg respectively) unchanged.
- **New finding, not fixed this pass — flagged for later**: `CombatEngine._determineOutcome`'s 2-arg shape means combat's fumble threshold always uses the difficulty-*adjusted* target, never the character's raw skill. For a raw skill over 100% facing a difficulty penalty that brings the target under 100, this could fumble on 99 as well as 100, where the rulebook's "skills over 100% fumble only on 00" arguably should still apply based on the *raw* skill. Distinct from the floor/ceiling bug just fixed, and would need a signature change (a third raw-skill parameter plumbed through combat context) rather than a drop-in fix — deliberately out of scope here.
- Live-verified against the running world: all four consumption points (`roll-math.js`, `combat-math.js`, `MythrasRoll.determineOutcome`, `CombatEngine._determineOutcome`) agree exactly on both the floor and ceiling cases; `game.system.api.determineOutcome` confirmed to be the literal same function reference as `roll-math.js`'s export, not a copy.
- 10 new tests (`combat-math.test.js`, `roll-math.test.js`) covering the floor and ceiling explicitly; 4 existing tests across `combat-math.test.js`/`roll-math.test.js`/`request-skill-check.test.js` updated in place — each was asserting the old buggy output for exactly the input ranges this fix changes. 495 → 505, all green.

## v1.4.255 — July 2026
- **`damageHooks` gains a numeric return: partial damage reduction, composing.** Previously the loop in `CombatEngine._applyDamage` (~L2649) only honoured a `false` return (full immunity, short-circuits the loop). Now a hook may return a finite number meaning "this is the new damage value" — floored to a non-negative integer (`Math.max(0, Math.floor(result))`) before the next hook runs. Any other return (`undefined`, `null`, `true`, a string, `NaN`) is ignored and the hook declines.
- **Composition, not override — deliberately the opposite of `weaponDamageHooks`.** Each subsequent hook receives the damage as already reduced by every earlier hook, so two independent reductions (e.g. a resistance power and a shield) both apply, rather than the first one winning. Two damage *formulas* can't both be true (hence `weaponDamageHooks`' first-wins), but two damage *reductions* legitimately can — this is why the two hook families use opposite composition rules, and the config doc now says so explicitly to head off a reader assuming they match.
- **`NaN` is explicitly excluded**, not just "any non-number": `typeof NaN === 'number'` is `true`, so `Number.isFinite` is doing real filtering work here, not defensive decoration — an unfiltered `NaN` would propagate into `system.current` and corrupt a hit location.
- `false` still short-circuits exactly as before: full immunity is absolute, nothing later can raise damage back up, and the opposed-Special-Effects resolution below the loop is unchanged (still fires unconditionally; SEs with no damage requirement, e.g. Trip Opponent, still resolve even when damage is fully blocked).

Notes that `ctx` carries `ctx.defender`, `ctx.weapon`, `ctx.hitLocationId`.
- **Judgement call surfaced, not resolved:** this loop has no `try/catch` around the hook call, unlike several other hook consumers in this codebase (e.g. `movementHooks` in `CharacterData.js`).
