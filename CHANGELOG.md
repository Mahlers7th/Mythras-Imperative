## v1.4.310 — August 2026
- **The system was public and effectively uninstallable, and this release fixes that.** `system.json` carried `url`, `manifest` and `download` as **empty strings**, so there was no manifest URL to paste into Foundry — there was no install path at all. And `packs/` is git-ignored (correctly: LevelDB is binary, is rewritten wholesale by `npm run pack`, and produces different bytes from identical source, so it does not belong in history), which meant anyone who cloned `Mahlers7th/Mythras-Imperative` by hand got the system with **twelve empty compendiums** — no standard or professional skills, no weapons, no armour, no spells, no creatures — unless they installed Node and ran the build themselves. The repo had 0 releases.
  - **Adds `.github/workflows/release.yml`.** On any push to master that changes `system.json`'s **version**, CI runs the tests and lint, builds the compendium packs with `npm run pack`, zips the runtime files with `system.json` at the zip root, and publishes a GitHub Release carrying both the zip and a standalone `system.json`. `npm` therefore runs on the CI runner and **never on a user's machine**: installing is one pasted manifest URL, and Foundry handles updates from then on.
  - **Triggered by a version change, not a git tag**, because the version bump already happens in the release commit itself — there is nothing extra to remember, and it matches the CHANGELOG convention this file already documents. Touching `system.json` without changing the version is a no-op, and an existing release for that version short-circuits the job, so a re-run or a revert cannot double-publish.
  - **Tests and lint gate the release, not just the repo.** A broken build must not become an installable package that Foundry then offers people as an update.
  - **The build asserts the packs are actually populated before publishing** — every declared pack must exist and contain at least one `.ldb`/`.log` file, or the job fails. An empty-compendium release is the precise failure this workflow exists to prevent, so it is checked rather than assumed. Verified locally against the current build: 12 packs, all non-empty.
  - **`manifest` and `download` do different jobs and are set accordingly.** `manifest` is a stable `releases/latest/download/system.json` URL — it is what Foundry re-checks for updates and must never be version-pinned. The **release asset's** `download` is pinned by the workflow to that exact version's zip, so installing an older release gets that release's files rather than the newest ones. The **committed** `system.json` instead points `download` at `releases/latest/...`, so it is never stale for a human reader or for anyone who installs by pasting the raw `system.json` URL.
- **Install URL**, for the README and for anyone asking: `https://github.com/Mahlers7th/Mythras-Imperative/releases/latest/download/system.json`
- No runtime code changed — this release is packaging only. 695/695 tests pass (9 suites), lint clean (0 errors, 75 pre-existing warnings).

## v1.4.309 — August 2026
- **Passion augmentation was rounded three different ways, and the chat card contradicted the roll.** Skill Augmentation adds 20% of the augmenting passion to the primary skill. `MythrasRoll.js` carried **four** separate inline copies of that arithmetic: the passion dropdown label (`:64`), the dialog's live DOM recompute of the target (`:128`) and the roll execution itself (`:165`) all used `Math.floor`, while the chat card's detail pill (`:235`) used `Math.ceil`. So a player augmenting with a 33% passion was offered **"+6%"** in the dropdown, rolled against a target built with **+6%**, and then read **"+7%"** on the resulting card. Visible in normal play, in a single interaction.
  - **Round up is correct**, on two independent grounds: the rulebook's general convention is that a fractional result always rounds up, and the augmentation rule's own worked example is explicit — a Locale of 33% augments Ride by **7%**, not 6%.
  - **Fixed by routing all four sites through `PassionData#augmentBonus`** (`module/data/ItemData.js`) rather than flipping three `floor`s to `ceil`. That getter already had the right implementation and — the reason this drifted at all — **zero callers anywhere in the codebase**. Four copies of a rule and one unused correct definition is exactly the shape that produces this bug; one definition with four readers cannot. Its doc comment now records that it is the single source.
  - **Nothing tested this.** Added five mirror-style tests in `tests/extension-hooks.test.js` covering the rulebook worked example, round-up behaviour, exact multiples, and an explicit guard asserting that `floor` would have given a different answer for eight of the values in the common range.
- **Doc fix, `mythras.mjs`:** the `game.system.api` block comment still claimed `combat-math.js` carries a duplicate `determineOutcome` pending dedup, and pointed at a known-issues entry for it. The dedup has already landed — `combat-math.js:20` re-exports the canonical `roll-math.js` function and holds no second copy. Corrected in place, with the history kept, so the next reader does not go looking for a duplicate that no longer exists.

## v1.4.307 — August 2026
- **`bashKnockbackMultiplierHooks` now combines by STRONGEST WINS (`Math.max`), was last-registered-wins by plain assignment. This fixes a live, silent bug in the consuming module.** `bash.js`'s loop applied each valid hook result with `knockbackMultiplier = result`, so whichever hook was registered last overwrote every earlier contribution. `destined-module` registers **three** independent, non-mutually-exclusive consumers — Enhanced Strength "Clobber" (×3, `:3406`), Combat Expert improvised weapon (×2, `:3462`), and Growth "Swat" (×2, `:3466`) — and `growthSwatBashMultiplier` registers last. A grown hero who spent a ×3 Clobber charge therefore received **×2**, with no error, no warning, and a chat card reporting the knockback as if correct.
  - **This was never a design decision.** `config.js`'s own comment recorded that a v1.4.278 doc/source sync pass found the docs claiming hooks multiplied together, checked `bash.js`'s actual loop, and **rewrote the docs to match the code** rather than fixing it. The same comment then advised "a single module hook owning net resolution" as the expected pattern — by which time the only consuming module had already registered three. The documented contract and the only real consumer had been contradicting each other since v1.4.270.
  - **Max over product (Chris's ruling).** A compounding product would have made Clobber + Swat ×6 — stronger than any single source claims. Max is the only option where nobody loses an effect they paid for and nothing becomes unexpectedly stronger. Consequence: independent hooks now compose safely, so a module no longer needs one hook resolving net effect across all its own powers (though that still works — a single hook returning its own max behaves identically).
  - Found by **Track 1 of the rules audit** (`rules-audit-spec.md`), whose purpose was to check whether the interaction model's seven combination kinds are all real before classifying hundreds of book mechanics against them. "Last-valid-wins" was the suspect kind; it turned out to be an accident of history *and* a live bug. **Net: seven kinds become six** — this family folds into the additive kind, whose definition widens to "contributions combined under the family's declared operator". Recorded in `editor-interaction-model-design.md` §2/§2a.
  - **The other suspect kind survived, against prediction.** `characteristicBonusHooks` (mutating visitor) was expected to reduce to "additive with a per-characteristic key". It does not: its consumer multiplies (Growth `siz × mult`, ×2 Titanic, ×4 Kaiju), floor-divides with a clamp (Shrinking, divisor scaled ×10/×1000 for Microscopic/Molecular Reduction), and adds (Morph's flat delta) — same field, order-dependent. Characteristic effects in this ruleset are multiplicative and divisive, not additive; an additive family could express only Morph. Kept as a real kind. Noted hazard, not acted on: its contract says hooks must not assume ordering, yet its operations are non-commutative — harmless with one consumer, not with two.
- No module changes required. All three Destined consumers keep working and now compose correctly.
- 690 tests pass (9 suites). New regression guard: `registration order does not affect the result` — the direct test for the bug above, which returned 2 instead of 3 under the old loop.
- **Live-verified in the running world** (Playwright, Foundry 14.366, world `mythras-imperative`, `destined-module@1.9.124` active): system loads at 1.4.307; `CONFIG.MYTHRAS.bashKnockbackMultiplierHooks` holds exactly the three Destined consumers named above; the shipped loop, executed in the live client against the module the server serves, returns **3** for ×3-then-×2 (the regression case, formerly 2), 3 for the full ×3/×2/×2 Destined trio, 1 with no hooks, 2 with invalid results ignored, and 3 with a throwing hook isolated. Hook array saved and restored — no state left in the world.
- Also adds a v14 architectural invariant to `system-CLAUDE.md`: **never write `system.json` with PowerShell `Set-Content`/`Out-File`** — PS 5.1 emits a UTF-8 BOM, which makes Foundry's manifest parser reject the file and drop the system from the systems list with no error. Learned the hard way during this build. The trap inside it: verifying with `node -e "require('./system.json')"` passes regardless, because Node strips BOMs silently.
- Committed as `74be6a1`

## v1.4.255 — July 2026
- **`damageHooks` gains a numeric return: partial damage reduction, composing.** Previously the loop in `CombatEngine._applyDamage` (~L2649) only honoured a `false` return (full immunity, short-circuits the loop). Now a hook may return a finite number meaning "this is the new damage value" — floored to a non-negative integer (`Math.max(0, Math.floor(result))`) before the next hook runs. Any other return (`undefined`, `null`, `true`, a string, `NaN`) is ignored and the hook declines.
- **Composition, not override — deliberately the opposite of `weaponDamageHooks`.** Each subsequent hook receives the damage as already reduced by every earlier hook, so two independent reductions (e.g. a resistance power and a shield) both apply, rather than the first one winning. Two damage *formulas* can't both be true (hence `weaponDamageHooks`' first-wins), but two damage *reductions* legitimately can — this is why the two hook families use opposite composition rules, and the config doc now says so explicitly to head off a reader assuming they match.
- **`NaN` is explicitly excluded**, not just "any non-number": `typeof NaN === 'number'` is `true`, so `Number.isFinite` is doing real filtering work here, not defensive decoration — an unfiltered `NaN` would propagate into `system.current` and corrupt a hit location.
- `false` still short-circuits exactly as before: full immunity is absolute, nothing later can raise damage back up, and the opposed-Special-Effects resolution below the loop is unchanged (still fires unconditionally; SEs with no damage requirement, e.g. Trip Opponent, still resolve even when damage is fully blocked).
